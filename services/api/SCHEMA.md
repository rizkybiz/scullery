## The tables, in plain words

**Core recipe content**

| Table | What a row is | Worth knowing |
|---|---|---|
| `recipe` | One recipe | `servings` (a number, for scaling) and `yield_text` ("12 cookies") are separate on purpose. `source_data` keeps the raw imported JSON so a better parser can re-read it later. `search` is a generated full-text column. |
| `ingredient` | One line of the ingredient list | Keeps `raw_text` (the original line) plus parsed fields: `quantity_min`/`quantity_max` (a range like "2-3 cloves"), `unit_code`, `food_id`, `name`, `preparation`, `note`. `section` groups lines ("For the sauce"). `sub_recipe_id` lets a line be another recipe. |
| `step` | One instruction | `timer_seconds` powers cooking-mode timers. Has `section` like ingredients. |
| `tag` / `recipe_tag` | A label and its link to recipes | `kind` (cuisine/course/diet/occasion/other) lets the UI group tags. Flat for now. |
| `media` | An image's metadata | The bytes live elsewhere (`storage_key`), so the storage backend can change without touching recipes. |

**Identity tables (the foundation for everything smart)**

| Table | What a row is | Worth knowing |
|---|---|---|
| `food` | A canonical ingredient ("all-purpose flour") | `is_staple` = assumed on hand. `category_code` groups the shopping list. `shelf_life_days` and `default_location` drive expiry hints. Names are unique case-insensitively. |
| `food_category` | A store-independent grouping (`produce`, `baking`, ...) | Seeded. `position` is the default order when no store is selected. Where a category sits in a *specific* store (aisle, walking order) is per-store data, added with the store tables. |
| `food_alias` | Another spelling of a food | "plain flour" -> all-purpose flour. Unique case-insensitively. |
| `unit` | A unit of measure, keyed by short code (`tbsp`, `g`) | `dimension` is volume/mass/count. `base_factor` converts to ml or g. Count units (clove, stick, can) never convert. Seeded in the migration. |
| `tool` / `tool_alias` | Equipment ("stand mixer") | `owned` is a plain flag since it's one household. |
| `recipe_tool` | "This recipe needs that tool" | `spec` holds "9x13 inch" and so on; `optional` marks nice-to-haves. |

**Pantry**

| Table | What a row is | Worth knowing |
|---|---|---|
| `pantry_item` | One purchase or lot of a food | `status` (in_stock/low/out) is the main signal. `quantity` is optional (and needs a unit when present). Several rows per food are allowed. |

## Decisions baked in

- **UUID primary keys** generated by the app (UUIDv7), no DB default. `unit` is the exception, with a readable text key.
- **Text + CHECK instead of ENUM types**: adding a value later is a one-line constraint change.
- **Deferred unique (recipe_id, position)** on ingredients and steps, so reordering can rewrite positions in one transaction.
- **Foods can't be deleted while referenced.** Merging duplicates means repointing references first, which is deliberate.
- **`updated_at` is maintained by a trigger** on the mutable top-level tables.

## What testing against a real Postgres showed

Applied through goose (up, down, up again), with sample recipes sharing flour, butter and salt in different spellings and units, then a shopping-list style aggregation:

```
item               bucket   qty(base)   have it
all-purpose flour  mass     500 g       yes     <- "plain flour" resolved via alias
all-purpose flour  volume   473 ml      yes     <- 2 cups; cannot merge with grams
butter             stick    1           no
butter             volume   29.6 ml     no      <- 2 tbsp; cannot merge with sticks
salt               volume   19.7 ml     yes     <- 1 tsp + 1 tbsp merged (staple)
```

What this tells us:
- **Aliases work**: two spellings became one line item.
- **Same-dimension units merge** (tsp + tbsp -> one number).
- **Cross-dimension units do not** (cups vs grams, tbsp vs sticks). Merging those needs per-food density data. This is the known limit we accepted; the shopping list will show both lines. A later `food_density` table can add the conversion without changing anything here.
- Aggregation must bucket count units by their own code, not by "count", or cloves and "each" would merge incorrectly.
- Ten bad inserts were all rejected (range with max < min, max without min, duplicate position, recipe as its own sub-recipe, duplicate food names/aliases, pantry quantity without a unit, bad unit definition, deleting a referenced food, blank recipe title).

## Known limits and things deliberately left out

- **Per-store layout is deferred.** Aisle depends on the store, so `food` carries only a store-independent category. Planned tables: `store`, `store_section` (walking order), `store_category_map` (which section a category lives in at that store) and `store_food_location` (per-food override). Resolution order: per-food override, then the category's section, then "unsorted" at the end. Learned from the two of you while shopping, not scraped.
- **Menu, shopping list and cook log tables aren't here yet.** They only reference tables that exist, so adding them later is purely additive.
- **Sub-recipe cycles beyond direct self-reference** (A uses B uses A) are not blocked by the database; the application must check.
- **Food/alias name collisions** (an alias equal to another food's name) aren't blocked by the database; the application checks.
- **The same tool twice in one recipe** (e.g. two different pans) isn't supported by the (recipe_id, tool_id) key. Probably rare enough, but it is a limit.
- **No `created_by`** columns until auth exists.
- **No seed foods/tools yet**; only units are seeded.
